# Deploying ProKit on Dokploy

Dokploy is the primary production environment for ProKit. It is the only place that can reach the private Supabase Postgres VM and is the canonical target for production deploys.

---

## Network model

- Production Postgres: Supabase VM at `10.0.2.4:5433`.
- The VM is in the same VNet/subnet as Dokploy.
- Only Dokploy containers can reach the database.
- All provisioning and migrations must run **inside** Dokploy.
- Vercel and other hosts are optional/secondary and must use a public endpoint or secure tunnel if used at all.

---

## Required environment variables

Use the values generated by `npm run prokit:bootstrap -- <app-slug>` as the single source of truth for Dokploy.

Example:

```bash
NODE_ENV=production
APP_SLUG=myapp
TENANT_DB_PASSWORD=<strong-password>

DATABASE_URL=postgresql://tenant_myapp_user:${TENANT_DB_PASSWORD}@10.0.2.4:5433/postgres?schema=tenant_myapp
SYSTEM_DATABASE_URL=postgresql://supabase_admin:<admin-password>@10.0.2.4:5433/postgres?schema=public

NEXT_PUBLIC_APP_URL=https://myapp.example.com
PORT=3000

Constraints:
	•	SYSTEM_DATABASE_URL must use an admin role that can:
	•	create schemas
	•	run Prisma migrations
	•	own tenant users/schemas
	•	DATABASE_URL must use the per-app tenant user created during bootstrap.
	•	APP_SLUG must match the slug used during provisioning; it is how scripts resolve the correct tenant.

⸻

Dokploy setup (required)

This is the only manual Dokploy configuration you need per app.

1. Bind mount for backups

The runtime gate takes a pg_dump backup before applying migrations. Backups must live on a shared host path so they survive container restarts.

In Dokploy UI:
	•	Path: App → General → Volumes/Mounts → Bind Mount
	•	Configure:
	•	Host Path: /var/backups/pgdump
	•	Container Path: /var/backups/pgdump
	•	Mode: read/write

Notes:
	•	Multiple apps may share the same host path.
	•	If this mount is missing or not writable, deploys will fail and the container will exit.

2. Runtime gate and start command

ProKit routes npm start through the runtime gate in scripts/runtime/start-prod.sh.
	•	Dokploy should simply run npm start as the container’s start command.
	•	The runtime script will:
	•	check for pending migrations
	•	take a pg_dump backup
	•	apply migrations
	•	run smoke checks
	•	restore from backup on failure
	•	exec the real app start command when everything passes

The actual app start command must live in scripts.start:app in package.json:
	•	Default: next start -p $PORT
	•	If your app needs a custom production start, change only scripts.start:app and keep npm start pointing at the runtime gate.

No other custom Dokploy commands are needed.

3. Postgres client tools

The deploy script relies on psql, pg_dump, and pg_restore.
	•	nixpacks.toml must be present in the repo to ensure Postgres 15 client tools are installed in the image.
	•	If you remove or change nixpacks.toml, you are responsible for making sure the client tools still exist, otherwise backups and migrations will fail.

First deploy checklist (production)

Use this before tagging the first production release:
	•	APP_SLUG, SYSTEM_DATABASE_URL, DATABASE_URL, and TENANT_DB_PASSWORD set in Dokploy env and consistent with .env.production.
	•	Bind mount configured: /var/backups/pgdump → /var/backups/pgdump (RW).
	•	nixpacks.toml present in the repo.
	•	package.json contains:
	•	scripts.start → runtime gate (scripts/runtime/start-prod.sh)
	•	scripts.start:app → actual Next.js start (next start -p $PORT by default)
	•	verify:deploy and any ProKit runtime scripts needed by the gate
	•	Domain and NEXT_PUBLIC_APP_URL configured.

Once this checklist is true:
	1.	Push your changes to main.
	2.	Create a tag (e.g. v1.0.0) that Dokploy listens to.
	3.	Dokploy will build the image, run npm start, and let the runtime gate decide whether the deploy is healthy.

⸻

Verify last deploy

You can re-run the deploy verification logic for a specific app slug:

APP_SLUG=myapp npm run verify:deploy

This:
	•	runs backup + migration + smoke checks using the same logic as the runtime gate
	•	is safe to run from CI or a one-off Dokploy container

⸻

Migrate existing projects to ProKit

To retrofit an older app repo to ProKit’s runtime model:

npm run prokit:migrate -- --apply

This will:
	•	align package.json with the runtime gate (npm start + start:app)
	•	ensure verify:deploy exists
	•	check for nixpacks.toml and required scripts
	•	update any ProKit-specific contracts it knows about

Review the diff before committing.

⸻

Make migrations explicit (required)

Dokploy deployments are not allowed to “just start the app” without passing through the gate.
	•	npm start must always run the runtime script.
	•	The runtime script must always:
	•	detect pending migrations
	•	take a backup
	•	apply migrations
	•	run smoke checks

If you bypass this by running next start directly in Dokploy, you lose:
	•	automated backups
	•	migration safety
	•	automated rollback

Do not change Dokploy to run next start directly.

Troubleshooting

Connection refused
	•	Verify the service is in the correct VNet/subnet.
	•	Exec into the Dokploy container and test:

psql "$SYSTEM_DATABASE_URL" -c "select 1;"


	•	If this fails, check:
	•	Security groups/firewall rules
	•	The actual VM IP and port
	•	That the DB service is running on Supabase/VM

Auth errors
	•	Confirm TENANT_DB_PASSWORD is the same in:
	•	the DB user you created
	•	DATABASE_URL
	•	any bootstrap scripts
	•	Ensure SYSTEM_DATABASE_URL uses the correct admin role with full privileges.

Migration failures
	•	Check Dokploy logs for the output of the runtime gate (deploy-prod.sh / start-prod.sh).
	•	Re-run migrations manually inside a Dokploy one-off container if needed:

npm run db:migrate:prod


	•	If restores are failing:
	•	Confirm the bind mount exists and is writable.
	•	Confirm pg_dump and pg_restore are available (via nixpacks.toml).

Runtime gate not running
	•	Make sure package.json still has:

"scripts": {
  "start": "scripts/runtime/start-prod.sh",
  "start:app": "next start -p $PORT",
  ...
}


	•	Verify scripts/runtime/start-prod.sh is executable (chmod +x).
	•	If Dokploy is configured to run anything other than npm start, fix it.
