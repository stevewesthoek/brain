# Deploying ProKit on Dokploy

Dokploy is the canonical production target for ProKit apps.

## Non-negotiables

- **Tag-gated deploys**: production deploys are triggered by git tags (no PR previews).
- **Hands-off production**: provisioning, migrations, backups, and smoke checks are executed automatically by the runtime deploy gate during container start.
- **Never bypass the gate**: Dokploy must start the app with `npm start` (which runs `scripts/runtime/start-prod.sh`).
- **Shared database only**: one Supabase/Postgres database per environment; apps are isolated by schema/role only; never create per-app databases.

## Required Dokploy setup (per app)

### 1) Environment variables

Set these in Dokploy env (values are typically generated by `npm run prokit:bootstrap -- <app-slug>` and copied from `.env.production`).

Required:

```bash
NODE_ENV=production
APP_SLUG=<repo_name>                 # must match the repo folder name
SYSTEM_DATABASE_URL=postgresql://<admin-user>:<admin-password>@<db-host>:5433/postgres
DATABASE_URL=postgresql://tenant_<slug>_user:${TENANT_DB_PASSWORD}@<db-host>:5433/postgres?schema=tenant_<slug>
TENANT_DB_PASSWORD=<alphanumeric_only_password>
PROCHAT_VERSION=<semver>             # must match the git tag without the leading "v"
```

Optional (slug rename support):

```bash
LEGACY_APP_SLUG=<old_slug>
```

Optional (last resort, destructive):

```bash
# If the deploy gate reports a migration-state mismatch (for example:
# - "db has migrations not present on disk"
# - "detected migrations: ... (migrations_table_missing)")
# allow the gate to reset the tenant schema/user and re-init from scratch.
PROKIT_RESET_TENANT_ON_MIGRATION_MISMATCH=1
```

Notes:

- `APP_SLUG` must match `[a-z0-9_]+` and must equal the repo name.
- `SYSTEM_DATABASE_URL` must be an admin connection that can create schemas/roles and run backups. (For Supabase, the admin user is typically `supabase_admin`.)
- `TENANT_DB_PASSWORD` must be alphanumeric only (no special characters).
- If your platform does not expand env vars inside other env vars, ProKit expands `${TENANT_DB_PASSWORD}` in `DATABASE_URL` at runtime (before running the deploy gate).

### 2) Backup bind mount (required)

The deploy gate stores backups under `/var/backups/pgdump/$APP_SLUG`.

Configure a bind mount in Dokploy:

- Host path: `/var/backups/pgdump`
- Container path: `/var/backups/pgdump`
- Mode: read/write

If the mount is missing or not writable, the deploy gate fails and the container exits (by design).

### 3) Postgres client tools (required)

The deploy gate requires `psql`, `pg_dump`, and `pg_restore`.

Keep `nixpacks.toml` in the repo so the image includes a matching Postgres client version.

## How production deploys work (runtime gate)

On container start:

1. `npm start` runs `scripts/runtime/start-prod.sh`
2. The runtime script runs `scripts/db/deploy-prod.sh`
3. The deploy script:
   - validates env
   - optionally renames a legacy tenant (`LEGACY_APP_SLUG`)
   - detects pending migrations
   - takes a backup when eligible
   - provisions the tenant (`db:init`)
   - applies migrations (`db:migrate:prod`)
   - runs a smoke check
   - restores from backup on failure (when a backup exists)
4. Only if the gate succeeds does it start the real app command (`npm run start:app`)

This is intentionally hands-off: operators should not be running ad-hoc production DB commands.

## Release flow (tag-gated)

1. Push changes to `main`.
2. Create an annotated semver tag `vX.Y.Z`.
3. Push the tag to origin (Dokploy listens to tags).
4. Dokploy builds and starts the container.

Recommended command:

```bash
git tag -a vX.Y.Z -m "vX.Y.Z"
git push origin vX.Y.Z
```

If Dokploy does not start a deploy after pushing the tag, re-emit the tag-create event for the same commit:

```bash
commit=$(git rev-parse vX.Y.Z^{})
git push origin :refs/tags/vX.Y.Z
git tag -d vX.Y.Z
git tag -a vX.Y.Z "$commit" -m "vX.Y.Z"
git push origin vX.Y.Z
```

## Rollback

Rollback is done by redeploying a previous tag (or creating a new tag pointing at a known-good commit).

Keep `PROCHAT_VERSION` aligned with the deployed tag.

## Common failure modes (fix in code/config, redeploy a tag)

- Backup mount missing/not writable (`/var/backups/pgdump`)
- Invalid or mismatched slug (`APP_SLUG` must equal repo name)
- Admin connection missing/underprivileged (`SYSTEM_DATABASE_URL`)
- Postgres client/server major mismatch (install matching client via `nixpacks.toml`)
- Migrations in a bad state (unfinished/rolled back)
